# Durable spot order contract

API: `/opex/v2/order`. All private reads and writes use the authenticated JWT subject; request JSON cannot choose an owner. POST and DELETE require `PERM_order:write` at the API and matching gateway.

POST JSON fields: `clientOrderId`, `symbol`, `type` (`LIMIT` or `MARKET`), `side` (`BUY` or `SELL`), `quantity`, `price`, and optional `postOnly` (default false). Decimal inputs should be strings. Symbol is the native uppercase `BASE_QUOTE` pair. Price is positive and represents the limit or bounded MARKET execution price; a MARKET is IOC and cannot spend above the BID reservation price. Post-only requires LIMIT/GTC. Client IDs are case sensitive, 1–80 characters from letters, digits, `.`, `_`, `:`, and `-`.

The receipt contains `clientOrderId`, `ouid`, `symbol`, `status`, nullable numeric `orderId`, `type`, `side`, `postOnly`, `quantity`, `price`, `filledQuantity`, `remainingQuantity`, nullable `reason`, and UTC ISO8601 `createdAt`. Decimal outputs are strings. `ACCEPTED_PENDING` means that the intent and submit outbox are committed, not that a numeric matching ID exists. `CANCEL_PENDING` is a received cancel request, not final cancellation. Actual statuses are `OPEN`, `PARTIALLY_FILLED`, `FILLED`, `CANCELED`, and `REJECTED`; numeric ID is assigned by matching admission.

GET and DELETE accept exactly one query parameter, `clientOrderId` or `ouid`. Another owner's identity gives404. Repeating a client ID with the same normalized parameters returns the same durable identity/state. Different parameters give409, even after terminal state. Decimal scale differences alone do not change the fingerprint. DELETE is idempotent and a fill can win a cancellation race.

GET `/opex/v2/order/owned` includes the caller's pending and active durable intents. Terminal intents remain individually queryable. GET `/opex/v2/order/events?cursor=0` returns up to500 caller-owned events ordered by a durable cursor; each item contains `cursor`, `ouid`, and JSON-string `payload`. Execution events identify real matching executions by `symbol:tradeId`. Fee settlement is obtained from native trade history, not fabricated from raw matching events.

Native reconciliation remains `/opex/v1/order/open`, `/opex/v1/user/history/trade`, and `/opex/v1/wallet/asset`. Trade `id` plus `symbol` is the execution identity; `commission` is the absolute fee in `commissionAsset`. BUY pays the received base asset and SELL pays the received quote asset. The initial reserve is ASK base quantity or BID quantity*price in quote. V1 cancellation remains available for legacy matching orders; v2 lookup/cancel applies to durable intents.

The gateway transaction records unique `(owner,clientOrderId)`, normalized payload SHA256, stable OUID, and outbox before publication. Delivery is at least once. An accountant admission row and deterministic reserve FA reference prevent duplicate reservation. Only a reserve marked PROCESSED after native wallet success is republished as confirmed admission. A definite native NotEnoughBalance refusal becomes REJECTED without refunding an amount never reserved; an ambiguous failed transfer stays pending for reconciliation.

Matching checks post-only against its current opposite best order before any fill, including equal ticks. CANCEL_TAKER STP stops the taker's remainder at its own maker, retains preceding other-owner fills, and emits no self execution or fee. Commands, terminal admission dedupe, pending cancellation, counters, and event outbox are saved together in the Redis snapshot. Snapshot writes and event publication are awaited before Kafka command acknowledgment. Refunds use one deterministic release reference and zero the unused reserve; ordered accounting events plus a transactional inbox deduplicate financial effects.

This integration uses one matching instance per pair, as the current service topology does. Do not scale concurrent matching owners or assume replica/rebalance fencing. Use durable Redis storage and preserve snapshots, Kafka offsets, intents, and accountant inbox together. Cross-database exactly-once is not claimed; verify wallet references, settlements and cursor replay in the isolated integration before enabling live-reference quoting.

Review round 1 progress guarantees: each resulting order-book update is keyed by pair and acknowledged within a 15-second timeout. Publication failure propagates to the command listener; snapshot/OUID replay protection and persisted Kafka offsets govern replay. An ambiguous admission ERROR is marked `reconciliation_required=true`, remains unpublished, and no longer blocks unrelated successful admissions or definite wallet refusals. Changing its financial action to PROCESSED makes it eligible again even while that flag is set. Owner event outcome transactions hold an owner-scoped PostgreSQL advisory lock before allocating the event cursor and through commit, so forward pagination across pairs cannot skip an earlier uncommitted event for the same owner.

For GET `/opex/v1/user/history/trade`, `id` is the persisted matching execution `trade_id`, scoped by `symbol`, and `orderId` is the caller's actual matching order ID. Both maker and taker views report the matched execution price and matched quantity. `quoteQuantity` is that fill's matched price multiplied by matched quantity, including partial fills; it is not the original order notional. Commission amount and asset come from the caller's maker or taker settlement columns. Native trade timestamps remain unchanged, and the API continues to serialize them as UTC epoch milliseconds.
